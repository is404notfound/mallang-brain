# 수익화·퍼블리싱 전략

정리일: 2026-09-09. 대상: 1인 개발 게임 **말랑두뇌음악대학**.

이 문서는 지금까지 나눈 사업 논의를 모은 기준 문서다. 연락·제출·계약은 아직 실행하지 않았다. 채널 정보는 2026-09-08~09 조사 내용을 기록했으며, 실제 연락과 출시 전에는 다시 확인한다.

## 결론부터

**같은 게임을 한글·영문으로 준비하고, 국내에서는 앱인토스 광고 수익을 직접 검증한다. 해외 Android 확장은 퍼블리셔의 테스트·홍보 지원을 받아 볼 수 있는 길로 준비한다.** Google Play도 무료+광고 출시 대상이다.

다만 퍼블리셔 계약이나 플랫폼 노출을 성공의 전제로 삼지 않는다. 먼저 플레이할 이유와 다시 돌아올 이유를 확인하고, 실제 광고 수익과 운영비를 비교한다. 유통처를 늘리는 것만으로 돈이 벌리지는 않는다.

무료 **상업 공개판**에는 광고를 넣는다. 기술 시험·비공개 구조화 플레이테스트에서 실제 광고를 빼는 것은 별개다. 이는 ‘처음에는 광고 없이 출시한다’는 뜻이 아니다.

기술 시험 기준은 [Gate 0 구현 계획](../02-gate-0/implementation-plan.md)을 따른다. 현재는 **Android와 Toss가 모두 통과해야 Gate 1을 시작**한다. 이 사업 문서가 그 조건을 바꾸지는 않는다.

## 4. 수익화가 어려운 이유를 다시 확인

이 게임은 아직 사업 성과를 확인하지 않았다. 따라서 아래는 ‘실패 원인 확정’이 아니라 **어디에서 막히는지 찾는 점검 구조**다.

발견 → 실행 → 첫 재미 → 재방문 → 광고 수익 → 비용을 뺀 이익.

| 막히는 곳                    | 먼저 볼 증거                                    | 바로 하면 안 되는 판단                                         |
| ---------------------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| 사람이 발견하지 못함         | 소개된 위치, 영상 노출, 클릭, 실제 신규 실행    | 영상만 올리면 누군가 알아서 볼 것이라고 기대                   |
| 클릭했지만 실행하지 않음     | 설치·로딩·오류, 첫 입력까지 걸린 시간           | 흥미 없는 게임이라고 즉시 결론                                 |
| 첫 플레이 뒤 떠남            | 입력 지연, 규칙 이해, 첫 실패 뒤 자발적 재도전  | 스킨·수집을 추가하면 해결된다고 가정                           |
| 다음 날 돌아오지 않음        | 신규 사용자의 D1·D7, 첫 복귀 행동               | 많이 플레이한 사람이 돌아왔으니 강제 반복도 효과가 있다고 해석 |
| 사람이 있어도 수익이 작음    | 실제 광고 노출·수익, 사용자당 수익, 국가별 차이 | 광고를 더 자주 보여주면 이익도 무조건 늘어난다고 가정          |
| 매출이 있어도 남는 돈이 없음 | 서버·운영·홍보·계약 비용과 개발자 작업 시간     | 매출을 순이익으로 표현                                         |

1인 개발자는 제작, 품질 확인, 홍보, 데이터 분석, 운영을 모두 맡는다. 재미가 부족한 경우와 홍보 인력이 부족한 경우는 처방이 다르다. [AppsFlyer의 게임 마케팅 보고서](https://www.appsflyer.com/resources/reports/gaming-app-marketing/)는 조사 대상 시장의 이용자 확보 경쟁을 이해하는 자료지만, 모든 1인 게임의 실패율이나 이 게임의 성공 확률을 알려 주지는 않는다.

## 5. 세 가지 대안 비교

여기서 ‘해결력’은 실제 문제를 해결하는지, ‘영향 범위’는 다른 일까지 얼마나 바꾸는지를 뜻한다.

| 대안                                        | 해결력                                                                      | 영향 범위                                          | 혼자 유지하기                                          | 현재 코드·방향과 맞는가                                        |
| ------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| A. 직접 출시·직접 홍보                      | 실제 플레이·광고 데이터를 얻기 좋음. 대규모 유입 부족은 남음                | 작음. 다만 홍보 부담을 전부 개발자가 짐            | 코드 관리보다 꾸준한 모집·운영이 부담                  | Unity 두 플랫폼과 무료+광고 방향에 맞음                        |
| B. 공통 게임 직접 검증 + 퍼블리셔 지원 협상 | 직접 검증의 자료와 외부 홍보 역량을 결합할 수 있음. 계약 불발 가능성은 남음 | 중간. 추가 SDK·보고·수정 요청·계약 범위 관리 필요  | 한 번에 한 테스트와 제한된 지원 범위라면 관리 가능     | 공통 게임을 유지하면 맞음. 현재 광고·현지화가 구현된 것은 아님 |
| C. 유료 완성판 판매                         | 적은 고객에게 가격을 받을 수 있지만 구매 설득·콘텐츠 분량 부담이 생김       | 큼. 상품, 출시 채널, 체험판, 홍보 계획을 다시 설계 | 출시 뒤 광고 운영은 줄어도 출시 전 제작·판매 부담이 큼 | 현재 무료+광고 합의와 다름. 지금 선택하지 않음                 |

**추천은 조건부 B다.** 직접 확인할 수 있는 범위는 진행하고, 홍보비와 운영 지원이 실질적인 퍼블리셔가 있으면 확장한다. 계약이 안 되면 A의 작은 직접 검증을 유지한다. 단, A가 큰 유입까지 대신 해결한다는 뜻은 아니다.

현재 저장소는 Gate 0용 구조와 환경 확인 코드 단계다. 광고·결제·현지화가 이미 완성되어 있다고 가정하지 않는다. 공통 게임 규칙과 플랫폼별 연결 부분을 분리하는 기존 방향을 유지하고, 사업 제안만으로 코드를 바꾸지 않는다.

## 6. 하나가 실패해도 전부 멈추지 않게 하기

아래는 앞으로 설계·시험할 실패 대응 원칙이다. 이미 구현했다는 뜻이 아니다.

| 일부 실패                | 전체로 번질 위험                                | 막는 방법                                                                                                    |
| ------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 퍼블리셔 거절·무응답     | 테스트와 출시가 계약 대기로 멈춤                | 독립적인 직접 테스트 경로 유지. 새 SDK 작업은 조건 확인 뒤 시작                                              |
| 크리에이터 무응답        | 홍보 계획 전체가 사라짐                         | 소규모 타깃 모집과 다른 제보처 병행. 영상 게재를 출시 조건으로 두지 않음                                     |

## 7. 광고와 이익을 판단하는 법

- 실제 연주 중에는 광고를 띄우지 않는다. 홈·결과는 위치 후보일 뿐, 배너·전면·선택형 광고와 빈도는 아직 확정하지 않았다.
- 광고를 본 사람이 공식 점수나 순위에서 유리해지지 않게 한다.
- 선택형 광고를 넣으려고 새 수집 시스템을 만들지 않는다. 유저가 원하는 보상이 없다면 보상형부터 고집하지 않는다.
- 광고를 못 받아도 기본 게임은 계속할 수 있어야 한다. 매번 광고가 반드시 재생된다는 뜻의 ‘광고 출시’가 아니다.
- 광고 수익뿐 아니라 광고 전후 이탈·재도전·재방문을 함께 비교한다.

**일 광고 매출의 단순 점검식:** 일 이용자 수 × 이용자당 실제 광고 노출 수 × 광고 1,000회당 실제 수익 ÷ 1,000.

형식·국가마다 광고 단가가 다르므로 실제 정산 자료로 나눠 계산한다. 광고 요청은 실제 노출과 다르다. 보고서 수익이 이미 수수료를 뺀 값이면 다시 빼지 않는다.

**남는 돈의 점검식:** 개발자 정산금 − 별도로 부담한 서버·도구·외주·홍보·운영비. 여기에 개발 시간의 비용도 따로 기록한다. 세금과 실제 계약의 정산 방식은 별도 확인한다.

‘광고비를 지원한다’가 ‘돌려주지 않아도 되는 돈’인지는 다르다. 수익에서 비용을 먼저 회수하는 계약이면 회수 순서·한도에 따라 개발자에게 들어오는 돈이 달라진다. 검증 전 예상 매출이나 성공 확률을 숫자로 단정하지 않는다.

월 목표 정산금, 감당할 운영비, 주당 운영 시간은 아직 미정이다. 공개 수익 검증 전에 정한다. 기존 재미 Gate의 D1 기준을 통과해도 흑자가 보장되는 것은 아니다.

## 8. 한글·영문 대응 범위

추천 방향은 **두 게임을 만드는 것이 아니라 같은 게임에 두 언어를 넣는 것**이다.

- 화면 문구를 코드·그림에 직접 박아 넣지 않고 교체할 수 있게 준비한다.
- 시작 안내, 입력 설명, 홈, 결과, 광고 안내, 오류 안내부터 목록을 만든다.
- 영어 길이와 글꼴 때문에 가로 화면 버튼이 잘리지 않는지 확인한다.
- 게임 규칙·점수·데이터 구조는 두 언어가 공유한다. 대사 많은 스토리와 음성 더빙은 먼저 만들지 않는다.
- 스토어 소개, 짧은 영상 자막, 제안서도 한글·영문 버전을 같은 원본에서 관리한다.
- 한국어·영어는 이용자의 국가와 같지 않다. 플랫폼, 언어, 유입 경로를 구분해 성과를 본다.

영문 게임명, 용어 번역, 기본 언어 선택, 구체적인 도구와 지원 화면은 [구현 전 체크리스트](../03-development/pre-implementation-checklist.md)에서 확정한다. 지금 문서화했다고 번역·개발이 완료된 것은 아니다.

## 9. 실제 실행 순서와 조건

1. **현재:** 문서의 충돌을 없애고 기존 Gate 0 기술 시험을 준비한다. 메시지 조사와 연락 후보 정리는 독립적으로 진행할 수 있다.
2. **Gate 0 통과 뒤:** 첫 콘테스트의 손맛과 자발적 재도전을 검증한다. 수집, 여러 악기, 여러 포털을 한꺼번에 붙이지 않는다.
3. **보여줄 실제 장면이 생기면:** 짧은 플레이 영상, 실행 링크, 한 장 소개, 측정한 수치를 준비한다. 수치가 없으면 없다고 쓴다. 공개 창구의 조건을 확인한 뒤 별도 실행 단계에서 제보·제출한다.
4. **공개 준비:** 두 필수 플랫폼의 광고, 오류 복귀, 언어, 계측, 등급·개인정보·음원 권리를 확인한다. 기술·구조화 테스트와 상업 공개 데이터를 섞지 않는다.
5. **유입·수익 검증:** 준비된 채널부터 순차 공개하되 두 플랫폼의 최종 범위는 유지한다. 실제 수익과 운영 부담을 확인하고, 퍼블리셔 테스트 지원이 유리할 때 확장한다.

퍼블리셔에게는 다음을 확인한다.

- 개인·1인 팀이 현재 계약할 수 있는지, 어떤 빌드·영상·지표가 필요한지.
- 테스트 광고비는 누가 내며, 실패하면 누가 부담하는지.
- 제출·테스트만으로도 독점, 우선 협상, 일정 기간 출시 제한이 생기는지.
- 게임 소유권, 국가·플랫폼별 배포 권리, 앱인토스 직접 운영 유지 여부.
- 매출 분배의 기준, 비용 회수 순서·한도, 정산 주기, 계약 종료 조건.
- 번역·광고 영상·품질 확인·운영을 누가 얼마나 맡는지, 1인이 감당할 수정 일정인지.
- 계정·원본 데이터·유저 지표 접근과 계약 종료 뒤 이전이 가능한지.

여러 곳에 문의할 수 있어도, 약관을 확인하지 않은 채 테스트를 동시에 약속하거나 같은 지역의 독점권을 중복으로 넘기지는 않는다.

## 10. 이번 재검토로 바뀐 계획

- ‘배포처를 많이 확보한다’에서 **국내 직접 광고 검증 + 해외 지원 협상**으로 우선순위를 좁혔다.
- 수집·스킨·새 플랫폼 대신 기존 콘테스트의 손맛, 재도전, 짧은 영상으로 전달되는 장면을 우선했다.
- 고정 6주 출시·종료 일정은 두지 않는다. 기술 시험의 시간 제한과 통과 기준은 별도로 유지한다.
- 초기 결제 상품 작업을 제외했다. 광고 형식·보상은 상세 설계 전까지 미정으로 남겼다.
- 퍼블리셔, 영상 소개, 광고 서버 등 하나에 전체 사업 흐름이 묶이지 않도록 실패 대응을 분리했다.
- 한글·영문 공통 대응은 계획에 반영했지만, Gate 예외·계약 권리·무광고 공개 예외는 승인된 것으로 처리하지 않았다.
