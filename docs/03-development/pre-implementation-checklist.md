# 구현 전 문서와 결정 체크리스트

사업 문서는 수익 모델·채널 선택의 기준, 제품 문서는 게임 규칙의 기준, Gate 0 문서는 기술 시험의 기준이다. 체크리스트만 고쳐서 기술 기준이나 계약 권한을 바꾸지 않는다. 충돌을 찾으면 해당 기준 문서와 결정 기록을 함께 고친다.

[초기 기획 보관본](../01-product/early-game-spec-archive.md)은 과거 기록이다. 그 안의 유료 상품·출시 일정·광고 가설은 현재 구현 지시가 아니다. 같은 내용을 담는 `office-hours-result(s).md`를 새로 중복 생성하지 않고 위 문서에 모은다.

## 2. Gate 0를 시작하기 전

- [ ] 현재 환경, Unity 버전, 기준 기기, Android·Toss 접근 권한을 개발 환경 문서에 따라 확인한다.
- [ ] 같은 빌드·측정 기록으로 두 플랫폼을 판정할 수 있게 준비한다.
- [ ] Gate 0 테스트 계획의 시험·결과 기록 위치를 정한다.
- [ ] 실제 Toss 샌드박스 측정이 불가능하면 `측정 불가`로 남긴다. 일반 WebGL 시험으로 Toss 통과를 대신하지 않는다.

이 단계에는 광고·결제·공식 랭킹·최종 번역·퍼블리셔 계약이 필요하지 않다. 기술 시험의 7영업일 기준과 재판정 규칙은 이번 문서 정리에서 바꾸지 않았다.

## 3. Gate 1 리듬 코어 구현 전에 만들 문서

**선행 조건은 기존대로 Android와 Toss Gate 0 모두 통과다.** 다음 문서는 아직 작성 완료가 아니다. Gate 0 측정 결과를 반영해서 작성한다.

- [ ] **Gate 1 구현 계획:** 실제 판정·점수·홀드·탈락·재도전 규칙, 12개 패턴과 20스테이지 조합표, 수용 테스트. 기술 시험용 판정 프로브와 제품 규칙을 구분한다.
- [ ] **사용자 테스트 기록 양식:** 모집 대상, 동의, 진단·독립 검증 집단, 제외 조건, 관찰 질문, 수정 가설과 판정 근거. 기존 인원·통과선을 임의로 바꾸지 않는다.
- [ ] **문구·현지화 설계:** 공통 문구 목록, 한글·영문 키, 용어표, 기본·대체 언어, 글꼴, 화면 길이 확인 방법. 정식 영문 번역 전체가 Gate 0 선행 조건은 아니지만 UI를 만들 때 문자열 구조를 정한다.
- [ ] **계측 설계:** 제품 문서의 이벤트·분모를 기준으로 수집 항목과 실패 기록을 정한다. 언어·플랫폼·유입 경로를 구분하고 기술 오류와 정상 이탈을 섞지 않는다.

파일을 많이 만드는 것이 목표는 아니다. Gate 1 구현 계획 안에 테스트·문구·계측 표를 먼저 모으고, 커질 때만 별도 문서로 나눈다.

## 4. 광고를 연결하기 전

- [ ] **광고 상세 설계:** 두 플랫폼별 지원 형식, 홈·결과 위치, 빈도 상한, 첫 노출 시점, 사용자 취소·복귀 흐름을 정한다.
- [ ] 선택형 광고를 채택한다면 보상의 목적·가치·지급 시점·중복 지급 방지·실패 처리를 먼저 정한다. 채택 자체는 아직 확정이 아니다.
- [ ] 광고가 없거나 느리거나 실패해도 재도전과 기본 플레이가 막히지 않게 한다.
- [ ] 광고 뒤 소리·박자·화면 방향·입력이 정상인지 실제 기기로 시험한다.
- [ ] 플랫폼별 SDK와 공통 리듬 코어의 경계를 정한다. 플랫폼별로 필요한 연결만 둔다.
- [ ] 첫 출시에 인앱결제·광고 제거 구매·상점이 들어오지 않았는지 확인한다.

## 5. 무료 상업 공개 전에

- [ ] 양쪽 최종 출시 범위를 유지하면서 실제 공개 순서와 책임을 정한다. 각 채널의 광고 연결·검증을 마친다.
- [ ] **출시 점검표:** 해당 게임의 등급·스토어·Toss 심사, 개인정보·광고 정책, 동의, 음악·미술·영상 사용 권리를 현재 공식 자료로 확인한다. 다른 게임의 등급 증빙을 그대로 쓰지 않는다.
- [ ] 초기 검증·공개 대상은 기존 제품 문서의 18세 이상 범위로 맞춘다. 이것만으로 모든 연령·개인정보 의무가 해결된다고 가정하지 않는다.
- [ ] **오류 대응표:** 광고·순위·분석·언어·네트워크 일부 실패에도 안전하게 복귀하는지 확인한다. 공식 순위 불가는 사용자에게 알린다.
- [ ] 한글·영문 필수 화면과 스토어·광고·오류 안내를 점검한다. 영문 게임명과 용어도 확정한다.
- [ ] **수익 검증표:** 신규 실행, 자발적 재도전, D1·D7, 광고 실제 노출·수익, 정산금, 비용, 작업 시간을 기록할 양식을 만든다.
- [ ] 월 목표 정산금·운영비 한도·운영 시간 한도를 정한다. 개발 시간과 현금 지출을 나눠 적는다.
- [ ] 비공개 시험·구조화 테스터·신규 공개 유저를 구분한다. 지표 누락을 확인하기 전 성공으로 판정하지 않는다.

## 6. 제보·제출·계약 전에

- [ ] 실제 플레이 영상, 바로 실행할 수 있는 링크, 한 장 소개, 확인한 지표와 아직 없는 지표를 준비한다.
- [ ] 국내용 한글과 해외용 영문 소개를 같은 내용으로 준비한다. 효능 주장이나 실제 유저로 오해할 연습생 표현을 넣지 않는다.
- [ ] 발송 직전 공식 창구·게시 규칙·소개 대상 플랫폼·무료 제보와 유료 협찬의 차이를 확인한다.
- [ ] 제출 전 약관에 테스트 독점·우선 협상·출시 제한이 있는지 확인한다. 제출 동의와 퍼블리싱 계약을 따로 검토한다.
- [ ] 계약 전 비용 부담·회수·분배, 지역·플랫폼 권리, 자료 접근, 종료·이전, 수정·운영 부담을 확인한다.
- [ ] 앱인토스 직접 운영과 해외 Android 권리를 나누고 싶다면 합의 내용을 계약에 반영한다. 현재는 협상안이지 확보된 권리가 아니다.

이 체크리스트는 발송이나 계약을 실행하라는 자동 승인서가 아니다.
