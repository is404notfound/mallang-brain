# 튜토리얼 화면·소리 반박 리뷰

현재 화면은 제공된 그림의 분위기를 살리지 못했다. 단순히 그림을 더 넣는 것으로 해결되지 않는다. 원본 토끼 표시, 악보 가독성, 입력 반응, 소리를 함께 고쳐야 한다.

검토일: 2026-10-11. 근거: 사용자가 올린 실행 화면, 제공 롭이어 PNG, 현재 튜토리얼 코드와 장면 파일. 주 리뷰와 별도의 읽기 전용 반박 리뷰를 수행했다. 이번 결과물은 개선안과 검토용 HTML 화면이다. Unity 구현 수정이나 새 음원의 청취 검증 결과가 아니다.

비교 화면: [세 방향 비교](tutorial-direction-review.html). 토끼와 뇌는 사용자 원본이다. 배경과 악기 도형은 방향 비교용이며 최종 그림이 아니다.

## 1. 현재 상태와 원인

| 문제 | 확인한 근거 | 판단 |
| --- | --- | --- |
| 원본 토끼가 표시되지 않음 | 실행 화면은 `DrawRabbit()`의 `rabbitAtlas == null` 분기와 일치한다 | 화면 기준 명확한 실패 |
| 파일은 복사되어 있지만 실행 중 연결이 검증되지 않음 | 원본과 프로젝트 PNG의 SHA-256이 동일하다. 장면과 PNG meta의 GUID도 동일하다 | 잘못된 그림을 복사한 문제는 아니다. 실제 import·로드 실패 지점은 아직 미확인 |
| 에셋 실패가 숨겨짐 | `Resources.Load`도 null이면 기본 도형으로 조용히 대체한다 | 연결 실패가 정상 완료처럼 보이게 한 직접적인 설계 문제 |
| 그림과 UI 재료가 다름 | 원본은 굵은 진갈색 선·종이 질감·아이보리·분홍색. UI는 큰 파란/분홍 패널·균일한 원·기본 회색 버튼 | 하나의 게임처럼 보이지 않음 |
| 흐린 글씨 | 첨부 화면의 제목·안내·악보 설명이 배경과 충분히 구분되지 않음. 스타일 글자색을 명시하지 않고 `GUI.color`만 변경 | 기본 GUI 스타일의 색 곱셈은 확인할 후보다. 흐림의 전체 원인으로 단정하지 않음 |
| 터치 영역이 글자판처럼 보임 | `DrawPad()`가 큰 ‘둥!/탁!’과 키보드 안내를 계속 표시함 | 기능 설명은 되지만 연주하는 재미를 보여 주지 못함 |
| 토끼와 뇌 변화가 너무 작음 | 큰 좌우 패널에 비해 캐릭터 비중이 작고 여백이 넓음 | 세계관의 핵심이 장식처럼 보임 |
| 소리가 임시 수준 | `MakePercussion()`이 사인파·배음·짧은 합성 잡음을 사용. 프로젝트에 녹음된 wav/ogg/mp3 타악기 파일 없음 | ‘둥/탁’ 구분은 시도했지만 음질의 완료 기준은 없음 |
| 예시와 입력 소리의 강도가 다를 수 있음 | 예시 volume 0.43, 입력 왼쪽 0.55·오른쪽 0.48. 입력은 좌우 pan, 예시는 중앙 | 같은 소리를 따라 치는 경험의 일관성을 확인해야 함 |

앞선 EditMode 138개·PlayMode 17개 통과는 진행과 판정에 대한 증거다. 원본 그림 표시, 배경 분위기, 음질이 좋다는 증거가 아니다. 원본 이미지 로드 테스트는 마지막 시험 뒤 추가되어 실행 결과가 없다.

## 2. 세 대안과 반박

세 안 모두 사용자 원본 토끼를 쓴다. 원본 중 뇌가 없는 큰 토끼와 가운데 분리된 뇌를 사용한다. 이미 뇌가 그려진 몸 위에 뇌를 덧대지 않는다. 작은 프레임에는 뇌가 함께 그려져 있으므로 이를 몸 애니메이션으로 사용하면 뇌 성장과 충돌한다. 초기에는 큰 원본 전체의 작은 기울임·눌림을 사용한다.

### A. 종이 위 작은 음악대 — 우선 추천

아이보리 종이 위에 토끼, 두 타악기, 악보가 놓인다. 진갈색 선을 공통으로 쓴다. 분홍색은 뇌·음표·짧은 성공 반응에 모아 둔다. 입력 영역의 큰 글자는 북과 림 타격 그림으로 바꾼다. 첫 안내에서만 왼손·오른손의 소리를 잠깐 보여 준다.

- 장점: 제공 토끼의 재료감과 가장 가깝다. 악보를 깔끔하게 유지하기 쉽다. 배경 1장과 입력 그림 2개로 시작할 수 있다.
- 반박: 종이 질감만 추가하면 현재 화면의 밋밋한 구조가 그대로 남는다. 매끈한 벡터 악기는 토끼와 다시 충돌한다. 악기 그림만 보고 손 역할을 이해할 수 있다는 보장도 없다.
- 수용 조건: 종이 질감은 배경에 약하게 둔다. 악보 뒤는 깨끗하게 비운다. 악기 선 굵기와 색을 원본에 맞춘다. 첫 안내는 손·음표·악기 반응이 함께 보여야 한다.

### B. 작은 연습실

작은 커튼, 낮은 바닥, 토끼, 두 악기가 연주 상황을 보여 준다. 방 소품을 거의 쓰지 않고 토끼가 듣고 연주하는 동작에 집중한다.

- 장점: 처음 보아도 음악을 연주하는 게임임을 전달하기 쉽다. 타격 반응을 악기와 몸짓에 연결할 수 있다.
- 반박: 배경과 소품이 중앙 악보와 시선을 경쟁한다. 엄지가 악기 반응을 가릴 수 있다. 귀를 따로 흔드는 애니메이션은 현재 원본만으로 자연스럽게 만들기 어렵다. 제작량이 가장 많다.
- 수용 조건: 악보 크기를 먼저 확보한다. 입력 반응의 일부가 엄지 위쪽에도 보이게 한다. 분리 귀 애니메이션보다 원본 전체의 작은 움직임을 먼저 쓴다.

### C. 말랑한 생각 구름

최초 참고 이미지의 종이·연보라 배경과 작은 별을 가져온다. 토끼와 뇌 뒤는 아이보리로 비운다. 움직이는 장식은 연주 중 멈춘다.

- 장점: 사용자가 처음 보여 준 분홍 뇌·연보라 이미지와 연결된다. 적은 배경 요소로 분위기를 만들 수 있다.
- 반박: 원본 토끼의 아이보리·갈색이 약해질 수 있다. 분홍 구름이 뇌와 겹치면 성장 반응이 묻힌다. 음악대보다 명상·감상 앱처럼 보일 수 있다.
- 수용 조건: 연보라는 가장자리의 넓고 옅은 영역에 제한한다. 악보와 뇌 뒤는 비운다. 악기·입력 반응으로 연주하는 행위를 계속 드러낸다.

| 비교 기준 | A 종이 합주 | B 연습실 | C 생각 구름 |
| --- | --- | --- | --- |
| 현재 제공 토끼와 일치 | 가장 직접적 | 방·악기 그림의 질감에 좌우됨 | 색을 절제해야 일치 |
| 악보를 읽기 쉬운가 | 유리 | 소품 절제가 필요 | 구름 대비 조절 필요 |
| 변경 범위 | 화면·입력 그림·배경 | 화면·배경·소품·동작 | 화면·배경·색 대비 |
| 추가 자산 제작량 | 비교적 적음 | 가장 많음 | 적음~중간 |
| 기존 코드와 연결 | 기존 두 줄 악보 유지 가능 | 기존 악보 유지 가능 | 기존 악보 유지 가능 |
| 유지보수 위험 | 자산 로드와 스타일 통일 | 소품·애니메이션의 상태 관리 증가 | 배경·뇌·음표의 대비 관리 |

추천은 A다. 이 추천도 조건부다. A를 구현한 화면에서 북이 클릭 영역임을 이해하지 못하거나 손그림 질감이 맞지 않으면 추천 근거가 사라진다. C의 연보라를 A에 무조건 섞는 것은 피한다. 먼저 A와 C를 각각 본 뒤 필요한 만큼만 결합한다.

## 3. 소리의 세 대안

현재 소리를 이번 리뷰에서 직접 청취하지 않았다. 사용자의 품질 지적과 합성 방식·설정 값을 근거로 평가했다. 새 소리를 만들지 않은 상태에서 ‘이 소리가 더 좋다’고 검증 완료로 말하지 않는다.

| 대안 | 소리 방향 | 장점 | 반박과 대응 |
| --- | --- | --- | --- |
| 1. 녹음된 타악기 샘플 — 우선 후보 | 왼쪽은 낮고 둥근 북, 오른쪽은 짧은 림/우드 타격 | 재질과 어택이 살아 있고 원본의 소박한 분위기와 연결하기 좋음 | 샘플 앞 무음·긴 울림·체감 음량 차이·사용권 확인 필요. 같은 음량으로 번갈아 들어 선택 |
| 2. 개선한 합성 타악기 | 낮은 몸통+짧은 어택, 높은 마른 타격. 끝을 부드럽게 닫음 | 추가 음원 없이 작은 용량으로 조절 가능 | 전자음 느낌이 남을 수 있음. 숫자 조정으로 음질이 좋다고 단정하지 않고 1안과 같은 패턴으로 비교 |
| 3. 사람 목소리 ‘둥/탁’ | 귀엽고 약간 어설픈 캐릭터의 짧은 발성 | 캐릭터성이 강하고 소리 이름을 배우기 쉬움 | 자음·모음 시작이 달라 목표 시점이 모호해질 수 있음. 반복하면 피로해질 수도 있음. 첫 시범·설명용을 우선 검토 |

‘샘플을 쓰면 무조건 좋다’도 반박한다. 울림이 길거나 시작이 흐린 녹음은 정교한 합성음보다 리듬게임에 불리하다. 선택 기준은 유명한 음원 여부가 아니라, 짧은 어택·낮음/높음의 구분·번갈아 칠 때의 만족감이다.

첫 비교에서는 배경 음악을 넣지 않는다. Perfect 보상음을 매번 겹치지 않는다. 먼저 연주음 자체가 좋아야 한다. 예시와 입력은 같은 클립·체감 음량을 기본으로 하고, 입력음을 박자에 강제로 맞춰 늦추지 않는다. 미리 준비한 짧은 AudioClip을 기존 DSP 시계로 예약 재생하는 방법은 기존 구조에서 사용할 수 있다. [Unity 예약 재생 설명](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AudioSource.PlayScheduled.html), [AudioClip 불러오기 설정](https://docs.unity3d.com/6000.3/Documentation/Manual/class-AudioClip.html).

## 4. 일곱 관점의 리뷰

점수는 현재 구현에 대한 주관적 진단이다. 개선안은 아직 Unity에서 확인하지 않았으므로 개선 후 점수를 올려 적지 않는다.

| 관점 | 현재 | 발견한 문제 | 개선안의 검증 기준 |
| --- | --- | --- | --- |
| 정보 순서 | 3/10 | 큰 패널이 토끼·악보보다 강함 | 처음 볼 때 토끼, 악보, 양손 연주가 한 시야에서 읽힘 |
| 상태 표현 | 4/10 | 자산 누락이 숨겨짐. 결과 버튼이 기본 스타일 | 로드 실패가 개발 로그·검사에서 드러남. 대기·시범·준비·연주·결과가 구분됨 |
| 첫 플레이 감정 | 3/10 | 귀여운 캐릭터와 연주하는 손맛이 약함 | 시범에서 기대, 입력에서 반응, 결과에서 짧은 뇌 변화를 경험 |
| 구체적인 디자인 | 2/10 | 큰 둥근 사각형·문자 패널·기본 버튼 | 원본 선·색·질감과 연결된 악기·악보·결과 버튼 |
| 디자인 규칙 | 2/10 | 현재 콘셉트용 색·선·글자 규칙 없음 | 종이 #F5EFDF, 진갈색 #382D28, 분홍 #E982A1을 후보로 검토. 최종 자산과 화면 대비 측정 후 확정 |
| 화면 크기·접근성 | 4/10 | Safe Area는 있으나 실제 가로 기기 검증 없음 | 16:9, 19.5:9, 태블릿에서 악보와 엄지 분리. 색 외에 음표 모양·줄 위치로 손 구분 |
| 미결정 사항 | 미결정 3건 | A/B/C, 실제 타악기 음원, 자산 실패의 실제 지점 | 방향 선택과 샘플 비교, 실제 장면의 import·로드 상태 확인 |

## 5. 상태와 화면 기준

| 상태 | 보이는 것 | 소리·입력 기준 |
| --- | --- | --- |
| PatternReady | 원본 토끼와 두 줄 악보. 짧은 준비 몸짓 | 예시와 입력 클립 준비. 판정 비활성 |
| Demonstration | 현재 음표와 토끼의 짧은 반응. 악보 항상 유지 | 준비된 같은 음원으로 시범. 사용자 입력은 채점하지 않음 |
| Countdown | 악보 유지. 짧은 준비 신호 | 첫 목표 박자가 언제인지 명확하게 전달 |
| PlayerPerformance | 악기 눌림·작은 반응·짧은 판정. 글자 패널 없음 | 즉시 연주음. 기존 판정 범위 유지 |
| Result | 뇌가 커지거나 조금 작아짐. 정확도 짧게 표시 | 연주를 덮는 긴 효과음 없음 |
| Transition | 다음 악보 준비 또는 같은 그림체의 다시 연주 버튼 | 예약 소리·입력·판정 초기화 |

16:9에서 터치 구역은 기존 30/40/30 비율을 출발점으로 한다. 악기 그림보다 실제 터치 영역은 넓게 잡는다. 19.5:9의 추가 폭은 터치 영역·안전 여백에 배분하고 악보를 늘려 글자를 흐리지 않는다. 태블릿에서는 토끼가 악보를 덮지 않도록 중앙 최대 폭을 둔다. 장식은 글자 뒤를 지나가지 않는다. 안내와 결과 글자 대비는 4.5:1 이상을 목표로 한다. 키보드 안내는 에디터에서만 표시한다.

뇌 애니메이션은 머리 영역 안에서만 움직인다. 원본 뇌를 별도 이미지로 둬 로직과 그림을 분리한다. 토끼를 크게 보이게 하더라도 악보와 겹치면 안 된다. 연주 중에는 화면 흔들림·확대·주요 배경 이동을 넣지 않는다.

## 6. 구현 순서와 확인 방법

1. **원본 연결 실패를 먼저 찾기.** 실제 실행 장면의 `rabbitAtlas` 참조와 `Resources.Load` 결과를 따로 확인한다. AssetDatabase 경로·import된 Texture2D·현재 프로젝트 경로를 확인한다. 근거 없이 시간 보정이나 임의의 다른 그림으로 대체하지 않는다. 실제 장면 캡처에서 제공 토끼와 분리된 뇌가 보여야 완료다.
2. **화면 방향을 고정하기.** A/B/C 비교 화면에서 자산·비율·배경을 확인한다. 검토용 도형 악기와 최종 손그림 악기를 혼동하지 않는다. 진갈색 글자·손그림 버튼·악보 색을 명시한다.
3. **튜토리얼 화면만 개선하기.** 기존 IMGUI를 고치면 변경 범위가 작지만, 기본 스타일 의존을 제거해야 한다. 프로젝트에 이미 있는 uGUI의 Image/RectTransform으로 교체하면 자산·배치·반응을 에디터에서 조정하기 쉽지만 초기 수정량이 늘어난다. 어느 경우든 Flow·판정·시계·콘테스트는 공통 기반으로 재사용한다. 새 UI 패키지는 필요하지 않다.
4. **소리 2~3쌍을 같은 패턴으로 비교하기.** 체감 음량을 맞추고 LR01/LR02에서 번갈아 재생한다. 낮음/높음 구분·어택·울림·반복 피로·조합의 만족감을 비교한다. 예시와 입력의 강도 차이를 확인한다. 미리 로드하고 타격 시작을 확인한다.
5. **코드 시험과 감각 시험을 각각 확인하기.** 기존 Unity 시험, 실제 장면 원본 표시, 두 패턴 완주, 다시 시작, 두 손 입력, 실패 뒤 복구를 확인한다. 배경을 지워도 악보·재생 위치·판정이 읽히는지 확인한다. 실제 기기 지연·오디오 정확도는 미측정으로 남긴다.

## 7. 실패가 전체 흐름에 번지지 않게 하기

- 필수 토끼 이미지 누락은 개발 단계의 검사와 로그에서 분명히 드러나야 한다. 기본 도형으로 정상 완료처럼 숨기지 않는다. 실행판의 복구 화면은 짧은 안내와 재시도를 제공한다.
- 배경 한 장을 못 읽으면 단색 종이 바탕으로 복구할 수 있다. 토끼·악보·판정은 계속 살아 있어야 한다.
- 타악기 클립 준비 실패는 시범 시작 전에 알린다. 소리를 못 들은 채 듣고 따라 하기 과제를 진행시키는 것은 핵심 경험을 깨뜨린다. 재시도 또는 명시적인 무음 연습 선택으로 복구한다.
- 자산 문제를 해결하려고 판정 엔진이나 기존 콘테스트를 다시 만들지 않는다.
